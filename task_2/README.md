# Решение задания 2 · Можно ли доверять модели-советнику SOC

Дашборд Taipy для руководителя SOC, который не занимается машинным обучением. Модель `wlarf-dec-jun-v3` оценивает каждую карточку: оценка ≥ 0,18 — «инцидент», карточка идёт в приоритет; ниже — модель её откладывает. Главная метрика дашборда — **доля реальных инцидентов, которые модель отложила** (пропуски).

На странице только вопросы, KPI-плитки и графики. Выводы с числами — в [`REPORT.md`](REPORT.md): его собирает `report.py` из тех же функций, что и плитки.

## Пять вопросов и почему выбран именно этот график

| # | Вопрос руководителя SOC | График | Почему именно он |
|---|---|---|---|
| 1 | **Сколько реальных инцидентов модель пропускает и меняется ли это со временем?** | Точки по неделям с 95 % интервалами и линией среднего | Главная метрика задания — доля пропусков, и её нужно видеть во времени. В неделе всего десятки–сотни инцидентов, поэтому у каждой точки есть интервал неопределённости: без него случайный скачок легко принять за поломку модели. Столбцы здесь хуже: длина столбца читается как количество, а показана доля с неопределённостью. Недели, где меньше 10 инцидентов, серые. |
| 2 | **Что даёт SOC разбор очереди в порядке модели?** | Кривая поиска (cumulative gains) с отметкой рабочего порога | Отвечает на вопрос руководителя на его языке: «разобрав X % очереди, найдём Y % инцидентов». Диагональ — очередь без модели, расстояние до неё — польза сортировки. Точка порога 0,18 показывает и выигрыш (сколько очереди отложено), и цену (какая доля инцидентов ушла в отложенные). ROC-кривая отвечает на другой вопрос, а её доля ложных срабатываний руководителю непонятна. |
| 3 | **Где модель «слепа»?** | Точечная диаграмма: доля пропусков по категориям IRP с 95 % интервалами | Нужно отличить систематическую ошибку от случайной. Если весь интервал категории правее средней линии, модель ошибается в ней систематически. Точки с интервалами компактнее столбцов и не прячут неопределённость. Подпись «N из M» отделяет частую ошибку от единичной. Категории, где меньше 10 инцидентов, не показаны. |
| 4 | **Можно ли верить уровню риска модели?** | Линейчатая диаграмма: доля реальных инцидентов на каждом уровне риска | Аналитик видит у карточки не оценку, а уровень риска («низкий»…«критический»), поэтому проверяем именно его: какая доля карточек каждого уровня — реальные инциденты. «Низкий» уровень разбит на две строки по порогу 0,18: так видно, что внутри одного «низкого» уровня есть и отложенные карточки, и карточки, которые модель подняла. Это расхождение шкалы риска и решения модели. Диаграмма калибровки была бы точнее, но уровни риска — язык SOC. |
| 5 | **Изменился ли поток карточек с тех пор, как модель обучали?** | Линии по месяцам основного датасета курса: доля реальных инцидентов и заполненность «Вендора»; подсвечены окно обучения и период работы | Показывает, почему модель могла устареть: изменились доля инцидентов в потоке и заполнение обогащения, от которого зависят признаки. Обе линии — доли от 0 до 100 %, поэтому они честно стоят на одной оси (без второй шкалы). Окно обучения неизвестно и подписано как предположение по названию версии. |

**KPI-плитки** над графиками: доля пропущенных инцидентов, доля очереди, которую модель отложила, доля подтвердившихся тревог модели, худшая категория, доля инцидентов с «низким» риском и доля инцидентов в потоке по сравнению с периодом обучения. Плитка с красной полосой — сигнал; пороги заданы в `views.py`.

**Цвета — как в задании 1:** оранжевый — реальный инцидент. Тёмно-красный — только пропущенные инциденты. Серые — фон, средние значения и данные, которых мало.

**Фильтры:** период работы модели (весь или один месяц) и критичность. Они действуют на все плитки и графики. В вопросе 5 месяц не фильтрует историю (там нужен весь ряд), а критичность фильтрует.

## Запуск

Нужны Python 3.12 и Poetry; зависимости те же, что для задания 1. Из корня репозитория:

```bash
poetry install
```

Положите в папку `data/` (в Git она не попадает):

| Файл | Где взять | Нужен для |
|---|---|---|
| `MODEL_PREDICTIONS_target.parquet` | папка задания 2, готовые данные | все вопросы: оценки модели и вердикты аналитиков |
| `iavd_ml_dataset.parquet` | папка задания 2, данные для обучения (≈300 МБ) | вопрос 5; без него на месте графика будет подсказка |

```bash
poetry run python task_2/app.py
```

Откройте http://127.0.0.1:5013. Отчёт:

```bash
poetry run python task_2/report.py
```

Проверки расчётов (без данных и без Taipy):

```bash
poetry run python -m unittest discover -s task_2
```

## Решения по данным

- **В метрики идут только карточки с вердиктом «Решён» (инцидент) или «False Positive»** — 15 839 из 19 393 оценок. Спам, дубликаты, «Нет ответа» и оценки без карточки (2 950) сверить с моделью не с чем.
- **Решение модели проверяется при загрузке:** у всех строк `y_pred` = «оценка ≥ 0,18» (порог 0,82 из `model_params` относится к классу FP, 1 − 0,82 = 0,18).
- **Файл карточек `iavd_incidents_raw3_target.parquet` не нужен:** нужные поля карточки (критичность, категория, вендор) уже есть в логе модели.
- **Окно обучения модели неизвестно.** По названию версии `wlarf-dec-jun-v3` считаем им декабрь 2024 — июнь 2025 и везде подписываем это как предположение.
- **Из основного датасета читаются только 4 столбца** (`Создан`, `Вердикт`, `Критичность`, `Вендор из сием`), поэтому файл на 300 МБ загружается за пару секунд.
- **Пропуск** — реальный инцидент с оценкой ниже порога. В жизни его всё равно разобрал аналитик: это то, что SOC потерял бы, если бы доверял модели без проверки.
- Даты и недели — по Москве.

### 2. Инференс модели

Модель отсортировала карточки по вероятности инцидента. Ваша задача — показать, что ей **можно или нельзя доверять**, и убедить в этом аудиторию, не связанную с машинным обучением: например, руководство SOC.

Сформулируйте **3–5 вопросов**, которые, как вам кажется, должен задать такой зритель, и ответьте на них наглядно.

Примеры вопросов:

1. Какие результаты были получены за период работы модели?
2. Как часто модель соглашается с вердиктом аналитиков SOC?
3. Зоны ошибок и их характер: модель ошибается случайно или систематически на каких-то признаках?
4. Общие характеристики модели во время эксплуатации в SOC.

…и так далее.

Помните: в SOC-контексте важны не столько общие метрики модели, сколько **доля пропущенных реальных инцидентов**.
