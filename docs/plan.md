# Командный проект по интеллектуальному анализу и визуализации данных


## 1. Суть задания

Разработать **интерактивный дашборд для анализа инцидентов информационной безопасности (SOC)** на основе предоставленного датасета. Приложение предполагается реализовать на Python с использованием **Pandas**, **Plotly** и **Taipy**.

Данные представляют собой исторические карточки инцидентов, а не поток событий в реальном времени. Поэтому задача приложения — **анализ накопленных инцидентов**, а не оперативный мониторинг поступающих алертов.

Предполагаемый пользователь — SOC-аналитик. Дашборд должен позволять оценить общую картину, сравнить группы инцидентов, выделить интересующие записи с помощью фильтров и просмотреть подробности отдельных карточек.

Основная последовательность обработки:

```text
Датасет SOC (Parquet)
          ↓
Загрузка и подготовка данных (Pandas)
          ↓
Расчёт показателей и построение графиков (Pandas + Plotly)
          ↓
Интерактивное приложение (Taipy)
```

## 2. Что должно получиться

Рабочая версия проекта должна включать:

1. **Подготовку данных.** Загрузка Parquet, проверка структуры и качества данных, необходимые преобразования.
2. **Аналитические показатели.** Расчёт выбранных KPI (ключевых показателей), например общего количества инцидентов, доли ложных срабатываний и числа критических инцидентов.
3. **Визуализации.** Графики динамики и распределений, отвечающие на конкретные аналитические вопросы.
4. **Интерактивность.** Фильтры по периоду, критичности и вердикту, изменение графиков и показателей при выборе фильтров.
5. **Просмотр карточек.** Таблицу инцидентов и подробную информацию о выбранной записи.
6. **Документацию и демонстрацию.** Инструкцию по запуску, описание принятых решений и показ работающего приложения.

Это **предлагаемый состав первой версии**, а не окончательный перечень обязательных функций.

## 3. Основные этапы работы

### Этап 1. Организация проекта

**Задача:** обеспечить совместную работу с единым кодом и окружением, чтобы не возникало расхождений в версиях библиотек и структуре файлов.

Предусмотрены GitHub для совместной разработки, Poetry для управления зависимостями и общая структура проекта. Изменения в основной ветке желательно объединять через Pull Request из рабочих веток участников.

**Текущее состояние:** создан репозиторий [data-analysis-visualization](https://github.com/brezginaor/data-analysis-visualization), настроен Python 3.12 и Poetry. Подробная установка описывается в `README.md`.

### Этап 2. Постановка аналитической задачи (DIKW)

**Задача:** определить, на какие вопросы должен отвечать дашборд и какие решения пользователь сможет принимать на основе показанных данных. Это необходимо сделать до окончательного выбора графиков.

Для SOC-кейса модель DIKW можно сформулировать следующим образом:

| Уровень | Применение к проекту |
|---|---|
| Data | Отдельные карточки: дата, критичность, тип, вердикт, источник |
| Information | Количество инцидентов, распределения по времени и категориям, доля FP |
| Knowledge | Какие типы и источники формируют наибольший поток событий, где особенно много ложных срабатываний |
| Decision | На какие группы событий обратить внимание, какие правила обнаружения стоит дополнительно проверить |

Дополнительно следует обозначить ограничения исходных данных и последствия ошибок классификации: **FP (False Positive)** создаёт ложную тревогу, **FN (False Negative)** означает пропуск реальной угрозы. Количество FN нельзя установить только по зарегистрированным карточкам.

**Результат:** 3–5 согласованных аналитических вопросов и краткая постановка задачи. При необходимости — отдельный документ `docs/dikw.md`.

### Этап 3. Исследование и подготовка данных (EDA)

**Задача:** проверить, можно ли корректно рассчитывать выбранные показатели. Например, перед построением графика времени обработки необходимо знать, что означают временные поля и в каких единицах записаны значения.

Исходные материалы находятся в общей папке на Яндекс Диске, раздел `1.5 Пр Декомпозиция/Dataset/`:

- `iavd_incidents_raw_target.parquet` — основной набор: **240 295 карточек, 97 полей**;
- `iavd_1000_incidents_raw_target.parquet` — выборка для первоначальной проверки;
- `iavd_incidents_raw_field_dictionary.md` — описание полей;
- `iavd_eda_questions.md` — набор вопросов и контрольных значений для EDA.

В рамках EDA проверяются типы данных, пропуски, уникальность `EntityId`, временной диапазон, распределения вердиктов, критичности, типов и источников инцидентов.

**Текущее состояние:** первичное исследование проведено в `notebooks/01_eda.ipynb`. Функция `load_incidents()` реализована в `src/data_loader.py`, возвращает данные с дополнительными признаками. Результаты, ограничения и выявленные проблемы описаны в [отчёте по данным](data_report.md).

Важно: не все поля пригодны для непосредственного расчёта показателей. В частности, поля `Время решения` и `Время Решения` содержат значения с неоднородной интерпретацией. Их использование для KPI требует дополнительной проверки.

### Этап 4. Выбор показателей и проектирование дашборда

**Задача:** связать каждую визуализацию с вопросом пользователя, а не просто вывести как можно больше графиков.

Для первой версии предлагается следующий набор элементов:

| Элемент | Содержание |
|---|---|
| KPI: количество инцидентов | Число карточек в выбранной выборке |
| KPI: доля FP | Доля карточек с вердиктом `False Positive` |
| KPI: критические инциденты | Число карточек с критичностью `Критическая` |
| Динамика инцидентов | Изменение количества карточек по времени |
| Распределение по критичности | Сравнение количества карточек разных уровней |
| Распределение по вердиктам | Сравнение категорий результатов обработки |
| Таблица инцидентов | Список записей с основными характеристиками |
| Карточка инцидента | Детали выбранного `EntityId` |

Минимальный ориентир — **3 KPI, 3 графика и таблица с просмотром карточки**. Конкретный набор согласовывается с командой после уточнения аналитических вопросов.

Также нужно выбрать визуальные кодировки: например, время показывать на временной оси, количество — длиной столбца, критичность — упорядоченными категориями и цветом. Цвета и подписи должны иметь единый смысл на всех графиках.

**Результат:** список показателей, эскиз интерфейса и краткое обоснование выбранных визуализаций (например, `docs/dashboard_design.md`).

### Этап 5. Расчёты и графики

**Задача:** отделить обработку и вычисления от интерфейса, чтобы графики и KPI можно было проверять независимо от Taipy.

Предполагаемое разделение:

- `src/analytics.py` — расчёт показателей и агрегирование данных;
- `src/charts.py` — создание графиков Plotly.

Для всех показателей нужно заранее определить правила подсчёта. Например, количество карточек по `EntityId` и сумма значений другого числового поля — разные метрики. При разборе многозначных полей (`~~||~~`) нельзя случайно увеличить общее число инцидентов.

После применения фильтров **все KPI, графики и таблица должны относиться к одной и той же выборке**.

**Результат:** функции расчёта и визуализации, которые принимают подготовленный DataFrame и не зависят от интерфейса.

### Этап 6. Интерфейс на Taipy

**Задача:** собрать расчёты и графики в приложение, которым можно пользоваться без изменения кода.

Предполагаемые функции первой версии:

| Возможность | Ожидаемое поведение |
|---|---|
| Выбор периода | Ограничивает данные по дате |
| Фильтр критичности | Оставляет выбранные уровни |
| Фильтр вердикта | Оставляет выбранные категории |
| Таблица | Показывает карточки текущей выборки |
| Сортировка | Меняет порядок отображения записей |
| Выбор карточки | Открывает сведения по `EntityId` |
| Сброс фильтров | Возвращает исходную выборку |

На первом этапе достаточно отображать в таблице основные поля; все 97 исходных столбцов одновременно выводить не требуется.

**Результат:** локально запускаемое Taipy-приложение с работающими фильтрами и связанными элементами интерфейса.

### Этап 7. Проверка работы

**Задача:** убедиться, что после объединения частей проекта приложение показывает согласованные данные и не ломается в типовых ситуациях.

Проверяются загрузка датасета, корректность KPI, согласованность фильтров, работа таблицы и карточки, поведение при пустой выборке и приемлемая скорость интерфейса.

**Результат:** проверенная рабочая версия приложения.

### Этап 8. Оформление и демонстрация

**Задача:** обеспечить воспроизводимый запуск и показать назначение приложения на понятном сценарии.

Итоговый `README.md` должен содержать установку зависимостей, расположение датасета, команду запуска, возможности интерфейса и известные ограничения. Демонстрационный сценарий: показать общие показатели, изменить фильтры, сравнить графики и открыть карточку выбранного инцидента.

**Результат:** исходный код, документация и демонстрация преподавателю.

## 4. Предлагаемое разделение работы на трёх участников

| Направление | Задачи | Результат |
|---|---|---|
| **Данные и инфраструктура** | Репозиторий, Poetry, загрузка Parquet, EDA, предобработка | `data_loader.py`, исследовательский ноутбук, отчёт по данным |
| **Аналитика и визуализация** | Аналитические вопросы, KPI, расчёты, графики Plotly | `analytics.py`, `charts.py`, обоснование графиков |
| **Интерфейс и интеграция** | Эскиз, Taipy, фильтры, таблица, просмотр карточек | Интерфейс приложения и интеграция расчётов |

Распределение предварительное. Общие решения — аналитические вопросы, состав показателей, схема данных и принцип фильтрации — необходимо согласовать до объединения кода. Части можно выполнять параллельно: аналитика работает с подготовленным DataFrame, интерфейс использует функции аналитики.

## 5. Связь с домашними заданиями по лекциям

Часть заданий можно выполнить на материалах общего проекта, не создавая отдельные приложения:

| Задание | Связь с проектом |
|---|---|
| DIKW для SOC | Постановка задачи и аналитических вопросов |
| Выбор 3–5 полей и визуальных кодировок | Обоснование графиков дашборда |
| Эскиз интерфейса | Макет Taipy-приложения |
| Траектория взгляда | Обоснование расположения KPI, графиков и таблицы |
| График «до/после» (Data-Ink) | Улучшение одной из визуализаций проекта |

Остаётся уточнить, требуется ли сдавать эти материалы отдельно от общего проекта. Аналогично, **не подтверждена необходимость отвечать на все 75 вопросов EDA**: объём анализа должен соответствовать назначенному варианту и требованиям преподавателя.
