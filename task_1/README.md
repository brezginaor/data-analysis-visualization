# Решение задания 1 · Карточки SOC

Дашборд Taipy для руководителя SOC. Он отвечает на **четыре вопроса** о наборе карточек инцидентов: из чего состоит поток, откуда берётся шум, работает ли приоритет критичности и когда SOC не укладывается в норматив.

На странице только вопросы, KPI-плитки и графики. Выводы с числами вынесены в отчёт [`REPORT.md`](REPORT.md): его собирает `report.py` из тех же функций, что и плитки, поэтому числа в отчёте и на дашборде совпадают.

Условия всех трёх заданий курса — в конце файла: [Условия заданий](#условия-заданий-курса).

## Четыре вопроса и почему выбран именно этот график

| # | Вопрос руководителя SOC | График | Почему именно он |
|---|---|---|---|
| 1 | **Из чего состоит поток карточек и как он менялся?** | Столбцы с накоплением по неделям, цвет — вердикт аналитика | Задача — «изменение во времени + состав». Высота столбца даёт объём, сегменты — состав, и всё это на одной временной оси. Недели сглаживают недельный цикл «будни/выходные», который на дневном графике превращается в пилу. Линия потеряла бы состав, круговая или 100-процентная диаграмма — объём. Для окна до 45 дней график переходит на дни. |
| 2 | **Какие правила корреляции создают больше всего шума?** | Линейчатая диаграмма с накоплением: 10 самых «громких» правил | Длина — самый точно считываемый канал для сравнения величин, а длинные имена правил читаются только по горизонтали. Цветовые сегменты позволяют сравнить распределение вердиктов по правилам корреляции. Низкая доля карточек с вердиктом «Решён» рассматривается совместно с долей карточек без вердикта, поскольку неполнота разметки ограничивает оценку эффективности правила. Подпись у конца столбца даёт число и долю потока, поэтому шкала не нужна. Sankey показал бы потоки, но не ранжирование; пузырьковая диаграмма для руководителя читается хуже. |
| 3 | **Берут ли критические карточки в работу быстрее остальных?** | Кривые накопленной доли (ECDF) по уровням критичности, логарифмическая шкала времени | Сравнивает распределения целиком и без выбора ширины корзин. Читается прямо как ответ: «за 15 минут взято N % критических». Медиана — точка пересечения с линией 50 %. Время тянется от секунд до суток, поэтому шкала логарифмическая. Гистограмма или violin скрыли бы ответ на вопрос «какая доля успела к сроку», а среднее исказил бы длинный хвост. Критическая — тёмная толстая линия, остальные уровни — оттенки серого, чтобы взгляд шёл к главному сравнению. |
| 4 | **Когда SOC не укладывается в SLA взятия в работу?** | Тепловая карта: тип дня × трёхчасовое окно суток, цвет — доля нарушений | Два категориальных измерения и одна величина: цвет кодирует интенсивность. Тип дня берётся из производственного календаря (`calendar.parquet`), поэтому праздники и предпраздничные дни не смешаны с обычными. Окна по 3 часа соответствуют планированию смен и дают достаточно карточек на ячейку. Показана доля нарушений, а не их число: число просто повторило бы профиль нагрузки. Ячейки, где меньше 5 карточек, оставлены пустыми, чтобы шум не выглядел фактом; «худшее окно» в плитке и отчёте выбирается только среди ячеек, где не меньше 100 карточек. Шкала одного цвета — от светлого к тёмному; доля подписана в каждой ячейке, поэтому отдельная цветовая шкала не нужна. |

**KPI-плитки** над графиками собирают критические числа: число карточек и среднее в день, долю False Positive, число реальных инцидентов, долю потока у топ-10 правил и сколько из них имеют менее 1 % карточек с вердиктом „Решён“, медиану взятия в работу у критических и долю нарушений SLA. Плитка с красной полосой слева — сигнал, на который стоит обратить внимание. Пороги заданы в `views.py`.

**Один цвет — один смысл:** оранжевый — реальный инцидент, синий — False Positive, серые — дубликаты, прочие и карточки без вердикта. Красная шкала используется только для доли нарушений SLA.

**Фильтры** в одной строке над всеми элементами: период (весь, 180 / 90 / 30 / 7 дней до последней даты в данных), тип дня (все, рабочие, выходные и праздники) и критичность. Фильтры действуют на все плитки и графики сразу.

## Запуск

Нужны Python 3.12 и Poetry. Из корня репозитория:

```bash
poetry install
```

Положите в папку `data/` (она не попадает в Git) файлы из папки задания 1 на Яндекс Диске:

| Файл | Нужен для |
|---|---|
| `iavd_incidents_raw_target.parquet` | основной набор, 240 295 карточек |
| `iavd_1000_incidents_raw_target.parquet` | учебная выборка: дашборд работает и на ней |
| `calendar.parquet` | тип дня (рабочий / пятница и предпраздничный / выходной / праздник) |

```bash
poetry run python task_1/app.py
```

Откройте http://127.0.0.1:5011. Если полного файла нет, дашборд сам возьмёт выборку из 1 000 карточек. Другой файл можно указать явно: `--data data/iavd_1000_incidents_raw_target.parquet`.

Пересобрать отчёт после смены данных:

```bash
poetry run python task_1/report.py
```

Проверки расчётов работают без данных и без запуска Taipy:

```bash
poetry run python -m unittest discover -s task_1
```

## Решения по данным

- **Читаются только 8 нужных столбцов** из 97, поэтому полный файл загружается за доли секунды. Существующий `src/data_loader.py` не менялся.
- **Время до взятия в работу** = `Дата взятия в работу` − `Создан`. Поля `Время решения` и `Время Решения` не используются: их единицы неоднородны, а `Время Решения` на деле хранит дату (см. `docs/data_report.md`). Поле `Период взятия в работу` совпадает с разницей дат и хранится в миллисекундах; проверено на выборке.
- **Отрицательные интервалы** (взятие раньше создания) считаются ошибкой данных: они исключаются, а не превращаются в ноль.
- **Карточки без даты взятия в работу** и карточки с некорректными временными интервалами исключаются из расчётов в вопросах 3 и 4. Их число и доля указаны в отчёте. В тестовой выборке поле `Период взятия в работу` принимает нулевое значение у всех 243 карточек без даты взятия в работу. Поэтому использование этого поля может привести к занижению времени реакции.
- **Нарушение SLA** = интервал больше `SLA по взятию в работу Атаки` (норматив в мс). На выборке расчёт совпадает с флагом `SLA просрочен (взятие в работу)` везде, где флаг заполнен, и дополнительно покрывает карточки, где флаг пуст.
- **Окна периода** отсчитываются от последней даты в данных. Таблица `dataframe.parquet` не используется: её окна заканчиваются 03.09.2025, на выборке (до 06.05.2025) они пусты, а «30 дней» в ней — это 28 дат.
- **Время и даты — по Москве.** Тип дня берётся из календаря; для дат, которых в нём нет, — по дню недели.
- **Учебная выборка не похожа на полный набор:** в ней 79 % карточек без вердикта и всего 5 реальных инцидентов. Выводы делаются по полному файлу, а выборка нужна, чтобы проверить, что дашборд работает.

## Условия заданий курса

Текст условий без изменений.

### Общее правило

Каждый элемент дашборда должны отвечать на вопрос: **«Почему я выбрал именно этот график?»**

---

### 1. Карточки SOC

Сформулируйте **3–5 вопросов** о наборе карточек, ответы на которые имеют практическую ценность, и представьте каждый ответ наглядно. Представьте, что вы будете показывать ваш дашборд руководителю SOC.

Примеры вопросов:

1. Из чего состоит поток карточек?
2. Какие признаки, правила или поля генерируют больше всего шума и алертов?
3. Сколько времени уходит на разбор карточки?

…и так далее. Список примеров не ограничивает вас: чем неочевиднее вопрос и чем точнее выбранное для него представление, тем выше результат.

---

### 2. Инференс модели

Модель отсортировала карточки по вероятности инцидента. Ваша задача — показать, что ей **можно или нельзя доверять**, и убедить в этом аудиторию, не связанную с машинным обучением: например, руководство SOC.

Сформулируйте **3–5 вопросов**, которые, как вам кажется, должен задать такой зритель, и ответьте на них наглядно.

Примеры вопросов:

1. Какие результаты были получены за период работы модели?
2. Как часто модель соглашается с вердиктом аналитиков SOC?
3. Зоны ошибок и их характер: модель ошибается случайно или систематически на каких-то признаках?
4. Общие характеристики модели во время эксплуатации в SOC.

…и так далее.

Помните: в SOC-контексте важны не столько общие метрики модели, сколько **доля пропущенных реальных инцидентов**.

---

### 3. SHAP-датасет

У нас есть решение модели и разложение этого решения по вкладам. Нужно сделать объяснение **понятным и проверяемым**.

Подумайте, на каком уровне показать вклады:

- для одной конкретной карточки;
- для группы похожих карточек;
- для всего потока сразу.

Старайтесь делать выводы понятными в первую очередь работникам SOC.

Постарайтесь найти хотя бы один случай, где объяснение модели подтверждается данными, и хотя бы один — где оно выглядит сомнительно.
